# Install PerfectPick to the home screen

The app cannot be installed. `frontend/public/sw.js` exists and serves push,
but nothing references a web app manifest, so no browser offers to add
PerfectPick to a home screen. Installing is most of what "feels like an app"
means on a phone: it opens full-screen, with no browser chrome, from an icon.

This adds the manifest, the icons it needs, and the one code change that makes
the app installable at all.

## What is actually missing

Three things, and only the first is the obvious one.

### There is no service worker unless the user enables push

`navigator.serviceWorker.register()` is called in exactly one place —
`frontend/src/lib/push.js:85`, inside `subscribe()` — and `subscribe()` returns
early unless `Notification.requestPermission()` resolves to `granted`. A user
who never taps "notify me" has no service worker at all.

Chrome's install prompt requires an active service worker, so a manifest alone
would leave the app installable only for people who had already opted into
notifications.

### The registration URL carries state

It registers `/sw.js?apiBase=…`, and `sw.js:71` reads that parameter back out
of its own `self.location` to re-subscribe on `pushsubscriptionchange`:

    const apiBase = new URL(self.location.href).searchParams.get("apiBase") || "";

So registration cannot simply be duplicated. Registering a bare `/sw.js` on
load produces a **second** registration under a different script URL, and the
re-subscribe path silently loses its API base — a failure that would surface
months later as "push stopped working for some people".

### There is no icon

`frontend/public/` holds `sw.js` and `vite.svg` — the Vite scaffold logo — and
`index.html` still points its favicon at it. A manifest needs 192px and 512px
raster icons plus a maskable variant, and iOS needs an `apple-touch-icon`
regardless of the manifest.

## Decisions

### `start_url` is `/drafts`, not `/`

Someone who installed the app is signed in and wants their drafts. `/` is the
landing page, which exists to explain the product to a stranger.

The accepted cost: a signed-out visitor who installs lands on a page that
bounces them to sign-in. That is a worse first launch for a rarer case, and the
alternative penalises every launch thereafter.

### Registration moves to app start, at the identical URL

The same `/sw.js?apiBase=…` string, query included, so there is exactly one
registration. `subscribe()` stops registering and waits on
`navigator.serviceWorker.ready` instead.

**Registering a service worker does not prompt for notification permission** —
those are separate browser APIs. So this is invisible to users who do not want
notifications, and it is what makes everyone able to install.

### Icons are generated by a committed script, using Playwright as the rasterizer

`frontend/scripts/make-icons.js` is the deliverable, not the PNGs it writes. A
binary nobody can regenerate is a binary that rots the first time the palette
changes.

Node cannot write a PNG on its own, and this project has no image library —
its dependencies are React, dnd-kit, oidc-client-ts and the Vite/ESLint
toolchain. Rather than add `sharp` or `canvas` for five files, the script uses
**Playwright, already a devDependency**: it opens the SVG in Chromium at each
target size and screenshots it. Zero new dependencies, and the rasterizer is
the same engine the test suite already runs.

The maskable variant keeps its content inside the inner 80% circle. Android
crops icons to whatever shape the launcher uses, and artwork that ignores the
safe zone loses its edges.

### `vite.svg` is deleted

It is scaffold residue, it is the current favicon, and leaving it would mean
shipping the Vite logo as part of a feature whose entire point is a recognisable
icon on a home screen.

## What ships

**`frontend/public/manifest.webmanifest`**

- `name` and `short_name`: "PerfectPick" — short enough to sit under an icon
  without truncation
- `start_url`: `/drafts`
- `display`: `standalone`
- `background_color` and `theme_color`: `#070A0F`, the ground `index.css`
  already paints, so the launch splash does not flash white before React mounts
- `icons`: 192 and 512 `image/png`, plus the 512 maskable with
  `"purpose": "maskable"`

**`frontend/index.html`** — `<link rel="manifest">`, `<meta name="theme-color">`,
`<link rel="apple-touch-icon">`, `apple-mobile-web-app-capable`,
`apple-mobile-web-app-status-bar-style`, and the favicon moved off `vite.svg`.

**`frontend/src/lib/push.js`** — a `registerServiceWorker()` export, called
once from `frontend/src/main.jsx` after the React root mounts, so registration
never blocks first paint. `subscribe()` stops registering and waits on
`navigator.serviceWorker.ready`.

The URL string lives in exactly one place so the two callers cannot drift
apart — the `?apiBase=` coupling described above is precisely the kind that
breaks when the same string is written twice.

**`frontend/scripts/make-icons.js`** and the five files it emits.

## Testing

Playwright can assert every static fact, and these are real regressions worth
catching:

- the manifest is linked from `index.html`, is served, and parses as JSON
- it declares 192 and 512 icons, `display: "standalone"`, and
  `start_url: "/drafts"`
- every icon URL it names actually resolves — a manifest pointing at a missing
  icon is the most common way this feature breaks silently
- the maskable icon is present and declares `"purpose": "maskable"`
- the service worker registers on load **without** a notification permission
  prompt being requested
- `subscribe()` does not create a second registration
- the registered script URL still carries `?apiBase=`, which is the coupling
  most likely to be broken by a well-meaning cleanup

## The acceptance check Playwright cannot perform

**Whether Chrome considers the app installable is decided by Chrome's own
heuristics, and this spec does not assert what they currently are.**

`sw.js` has no `fetch` handler — only `push`, `notificationclick` and
`pushsubscriptionchange`. Chrome has historically required a fetch handler for
installability. The requirement that the app serve a working offline response
was relaxed at some point; whether the handler itself is still checked is not
something this spec claims to know.

So the acceptance check is performed against a real browser, not asserted:

1. Load the deployed site in Chrome.
2. Open DevTools → Application → Manifest and read the installability verdict.
3. If it reports a missing fetch handler, add a minimal one to `sw.js` and
   re-check.

A test suite that passes while the app is not installable would be this
feature's version of the mistake the run factor already made once — green
tests over a broken claim. The browser's own verdict is the only thing that
settles it.

## Out of scope

- **Offline support.** A draft is inherently online: it reads a shared clock and
  writes picks through conditional writes. Caching the shell would add a cache
  invalidation problem for no working offline experience.
- **A custom install prompt.** `beforeinstallprompt` with a styled button is a
  separate feature with its own dismissal-state questions.
- **Screenshots and `shortcuts` in the manifest.** They enrich the install
  dialog on Android. Worth having, not worth blocking on.
- **Designing a brand.** The generated mark uses the palette the app already
  has. It is consistent, not designed, and a real icon should replace it if one
  ever exists.
